PART I: BUILDER DESIGN PATTERN

1. Pattern Name

Builder Pattern

2. Category

Creational Design Pattern

3. Intent

The Builder Pattern separates the construction of a complex object from its internal representation, allowing the exact same construction process to produce diverse types and configurations of an object. It enables incremental, step-by-step assembly rather than forcing clients to pass massive argument lists to overloaded constructors.

4. Problem Statement

In modern software engineering, objects frequently contain many attributes—some mandatory and many optional. In our real-world scenario of a Custom Desktop Computer Assembly System, an assembled PC contains: Motherboard, Processor, RAM, Storage (NVMe/SATA), Graphics Card, Power Supply, Liquid/Air Cooling, and Wi-Fi modules.

A conventional constructor-based implementation suffers from:

  • Telescoping Constructor Anti-Pattern: Overloading constructors with 5, 6, 7, or 8+ parameters becomes completely unmaintainable.
  • Parameter Ordering Confusion: Consecutive parameters sharing identical types (e.g., strings or integers) lead to silent logical bugs when values are mistakenly swapped.
  • Inconsistent Object State: Using a parameterless constructor followed by public setters leaves the object in a partially initialized, unstable state while being configured.

5. Motivation: Why Normal Implementation is Poor

In a direct constructor design, constructing an office PC without a dedicated GPU or liquid cooling forces callers to pass empty strings or null pointers:

Computer officePC("MSI B760", "Intel i5", "16GB", "512GB", "", "550W", "Stock Fan", false);

Adding new hardware options directly modifies existing constructors, breaking existing client code and violating the Open/Closed Principle (OCP). The Builder Pattern decouples assembly logic into dedicated builder objects, completely resolving this problem.

6. Pattern Structure (UML Class Diagram)

7. Class Responsibilities

  • Computer (Product): The complex domain object storing hardware specifications and providing displaySpecifications().
  • ComputerBuilder (Builder Interface): Declares pure virtual construction steps (buildMotherboard(), buildCPU(), buildGPU(), etc.) and getResult().
  • GamingComputerBuilder (Concrete Builder 1): Assembles top-tier gaming components (Intel i9-14900K, RTX 4090 24GB, 64GB DDR5, 360mm AIO cooler).
  • OfficeComputerBuilder (Concrete Builder 2): Assembles cost-effective office components (Intel i5-13400, integrated UHD 730, stock air cooling).
  • ComputerAssembler (Director): Encapsulates standard assembly workflows (constructFullPC(), constructMinimalPC()).
  • Client (main): Configures the Director with the appropriate Builder, initiates assembly, and consumes the final product.

// ==========================================
// 2. BUILDER INTERFACE
// Declares step-by-step construction methods.
// ==========================================
class ComputerBuilder {
public:
    virtual ~ComputerBuilder() = default;
    virtual void reset() = 0;
    virtual void buildMotherboard() = 0;
    virtual void buildCPU() = 0;
    virtual void buildRAM() = 0;
    virtual void buildStorage() = 0;
    virtual void buildGPU() = 0;
    virtual void buildPowerSupply() = 0;
    virtual void buildCooling() = 0;
    virtual void buildNetwork() = 0;
    virtual std::unique_ptr getResult() = 0;
};

// ==========================================
// 5. DIRECTOR
// Defines the sequence of construction steps.
// ==========================================
class ComputerAssembler {
private:
    ComputerBuilder* builder;

public:
    void setBuilder(ComputerBuilder* b) {
        builder = b;
    }

    // Construct a complete standard configuration
    void constructFullPC() {
        if (!builder) return;
        builder->reset();
        builder->buildMotherboard();
        builder->buildCPU();
        builder->buildRAM();
        builder->buildStorage();
        builder->buildGPU();
        builder->buildPowerSupply();
        builder->buildCooling();
        builder->buildNetwork();
    }

    // Construct a minimal budget/headless server configuration
    void constructMinimalPC() {
        if (!builder) return;
        builder->reset();
        builder->buildMotherboard();
        builder->buildCPU();
        builder->buildRAM();
        builder->buildStorage();
        builder->buildPowerSupply();
    }
};

    std::cout << "========================================================\n";
    std::cout << "       CSE 3206 LAB 3 - BUILDER PATTERN DEMO           \n";

    ComputerAssembler assembler;

    // 1. Building a High-End Gaming PC via Director
    std::cout << "[Step 1] Assembling High-End Gaming PC via Director...\n";
    GamingComputerBuilder gamingBuilder;
    assembler.setBuilder(&gamingBuilder);
    assembler.constructFullPC();
    std::unique_ptr gamingPC = gamingBuilder.getResult();
    gamingPC->displaySpecifications();

    // 2. Building a Standard Office PC via Director
    std::cout << "[Step 2] Assembling Standard Office Workstation via Director...\n";

    assembler.constructFullPC();

    std::cout << "[Step 3] Custom Customization: Assembling Custom Barebones Server...\n";
    officeBuilder.reset();
    officeBuilder.buildMotherboard();
    officeBuilder.buildCPU();
    officeBuilder.buildRAM();
    officeBuilder.buildStorage();
    officeBuilder.buildPowerSupply();
    // Intentionally skipped GPU, RGB cooling, Wi-Fi card
    std::unique_ptr customServer = officeBuilder.getResult();
    customServer->displaySpecifications();

    std::cout << "Builder Pattern demonstration executed successfully.\n";
    return 0;
}

9. Execution Flow

  1. Instantiation: Client creates a Director (ComputerAssembler) and a Concrete Builder (GamingComputerBuilder).
  2. Configuration: Client assigns the builder to the director via assembler.setBuilder(&gamingBuilder).
  3. Step-by-Step Construction: Director executes constructFullPC(), which calls builder steps in exact logical sequence.
  4. Product Retrieval: Client calls gamingBuilder.getResult(), safely extracting the completed product and resetting the builder.
  5. Director-Free Custom Build: For custom variations (e.g. headless server), the Client drives builder steps directly without Director intervention.

10. Advantages

  • Fine-Grained Construction Control: Construction can be executed in distinct steps or deferred until prerequisites are ready.
  • Single Responsibility Principle (SRP): Isolates complex assembly logic from the domain representation of the product.
  • Open/Closed Principle (OCP): New configurations (e.g., ServerBuilder) can be added without altering existing code.
  • Eliminates Telescoping Constructors: Clean, readable code without messy multi-parameter signatures.

11. Limitations

  • Increased Class Count: Requires defining builder interfaces, concrete builders, and directors, adding architectural overhead for simple objects.
  • Coupling to Product Structure: Builders must be updated whenever fundamental product structure changes.

12. Real-Life Applications

  • Custom PC & Automobile configurators (Dell, Tesla).
  • Multi-format document generation engines (compiling into PDF, HTML, or DOCX).
  • SQL & HTTP query builders (constructing SELECT, WHERE, JOIN clauses dynamically).

13. Industry Examples

  • Java Core: java.lang.StringBuilder, java.nio.ByteBuffer.
  • Android Framework: android.app.AlertDialog.Builder.
  • Spring Framework: UriComponentsBuilder, MockMvcRequestBuilders.
  • Apache Commons: RequestBuilder.

15. Conclusion

The Builder Pattern is the gold standard for constructing complex aggregate objects with many optional properties. It guarantees encapsulation, prevents invalid intermediary states, and upholds SOLID object-oriented design principles.

PART II: PROTOTYPE DESIGN PATTERN

1. Pattern Name

Prototype Pattern

2. Category

Creational Design Pattern

3. Intent

The Prototype Pattern specifies the kinds of objects to create using a prototypical instance, creating new objects by copying this prototype via a virtual clone() method. It shields client code from concrete instantiation classes and eliminates expensive initialization costs.

4. Problem Statement

In real-time software systems such as Game Engines (RTS / RPG), Graphics Editors, and Virtual Reality platforms, creating complex objects from scratch is computationally expensive. Spawning an enemy unit (Swordsman, Archer, Mage) requires reading 3D models and textures from storage, compiling audio waveforms, parsing skill trees from JSON/XML configs, and calculating attribute curves.

Calling new Swordsman(...) dozens of times during real-time gameplay creates severe frame drops and stalls. Furthermore, hardcoding instantiation logic couples the spawner directly to concrete unit classes.

5. Motivation: Why Normal Implementation is Poor

  • Expensive Initialization Overhead: Re-executing file I/O, asset decompression, and attribute parsing for identical units is redundant and slow.
  • Tight Coupling: Client spawner classes become tightly coupled to concrete unit classes, violating the Dependency Inversion Principle (DIP).
  • Polymorphic Object Copying: In C++, if a client holds only an abstract base pointer (GameUnit*), it cannot invoke new Derived() because the exact derived class is unknown at compile time. The Prototype pattern's virtual clone() provides seamless polymorphic copying.

6. Pattern Structure (UML Class Diagram)

7. Class Responsibilities

  • GameUnit (Prototype Interface): Declares pure virtual clone() method and unit operations (render(), setPosition(), setCustomName()).
  • Swordsman (Concrete Prototype 1): Stores heavy melee combat data and implements clone() via copy constructor.
  • Archer (Concrete Prototype 2): Stores ranged combat data and implements clone().
  • Mage (Concrete Prototype 3): Stores magic spell arrays and implements clone().
  • UnitRegistry (Prototype Cache / Spawner): Maintains a hash map of master pre-initialized prototypes and handles clone requests by key.
  • Client (main): Registers master prototypes, spawns clones dynamically on the battlefield, adjusts runtime properties, and deploys units.

class GameUnit {
public:
    virtual ~GameUnit() = default;
    
    // Core Prototype clone interface (pure virtual)
    virtual std::unique_ptr clone() const = 0;
    
    // Presentation / gameplay method
    virtual void render(int unitId) const = 0;

// 2. CONCRETE PROTOTYPE 1: Swordsman / Warrior

class Swordsman : public GameUnit {
private:
    std::string unitType;
    std::string customName;
    int health;
    int attackPower;
    int armor;
    std::string weapon;
    int posX = 0;
    int posY = 0;

public:
    Swordsman(const std::string& name, int hp, int atk, int def, const std::string& wpn)
        : unitType("Swordsman"), customName(name), health(hp), attackPower(atk), armor(def), weapon(wpn) {
        // Simulating expensive initialization (asset loading, audio preload, skill tree compilation)
    }

    // Copy constructor used for cloning
    Swordsman(const Swordsman& other)

          customName(other.customName),
          health(other.health),
          attackPower(other.attackPower),
          armor(other.armor),
          weapon(other.weapon),
          posX(other.posX),
          posY(other.posY) {}

    // Implement clone() using copy constructor
    std::unique_ptr clone() const override {
        return std::make_unique(*this);
    }

    void setPosition(int x, int y) override {
        posX = x;
        posY = y;
    }

    void setCustomName(const std::string& name) override {
        customName = name;

                  << "    Weapon: " << weapon << "\n"
                  << "    Coord : (" << posX << ", " << posY << ")\n\n";

// ==========================================
// 5. PROTOTYPE REGISTRY / SPAWN MANAGER
// Caches master prototypes and clones them on demand.
// ==========================================
class UnitRegistry {
private:
    std::unordered_map> prototypes;

public:
    void registerPrototype(const std::string& key, std::unique_ptr prototype) {
        prototypes[key] = std::move(prototype);
    }

    // Creates a new unit instance by cloning the registered prototype
    std::unique_ptr spawnUnit(const std::string& key) const {
        auto it = prototypes.find(key);
        if (it != prototypes.end()) {
            return it->second->clone(); // Returns deep cloned copy
        }
        std::cerr << "Error: Prototype with key '" << key << "' not registered!\n";
        return nullptr;
    }
};

9. Execution Flow

  1. Prototype Pre-caching: During system boot, master unit templates are created once and stored in the UnitRegistry.
  2. Clone Request: At runtime, the client requests a unit: registry.spawnUnit("elite_swordsman").
  3. Virtual Clone Execution: The registry finds the master instance and calls clone(), invoking the derived copy constructor.
  4. Dynamic Mutation: The client configures instance-specific fields (e.g., coordinates, unit nicknames) without mutating the master prototype.
  5. Deployment: The freshly cloned unit is added to the active unit list with zero initialization delay.

10. Advantages

  • Blazing Fast Object Creation: Bypasses expensive asset loading, constructor calculations, and disk/network I/O.
  • Polymorphic Cloning: Duplicates objects through base pointers without coupling to concrete classes.
  • Runtime Dynamic Configuration: Prototypes can be registered, replaced, or removed dynamically without recompiling.
  • Reduces Subclass Explosion: Pre-configured presets can replace deep subclassing hierarchies.

11. Limitations

  • Deep vs. Shallow Copy Nuances: Cloning objects containing circular references or dynamic raw pointers requires meticulous deep-copy handling to prevent double-free or memory corruption.

12. Real-Life Applications

  • Real-Time Strategy / RPG Game enemy and projectile spawning.
  • Graphic vector applications (copy-pasting complex vector shapes in Illustrator / Figma).
  • Virtual Machine and container provisioning (spawning containers from master image snapshots).

15. Conclusion

The Prototype Pattern provides an optimal mechanism for high-frequency object generation where instantiation cost is significant. Combined with a centralized Prototype Registry, it maximizes runtime efficiency while maintaining clean object-oriented decoupling.

SUMMARY COMPARISON OF CREATIONAL DESIGN PATTERNS

Feature / Criteria Builder Pattern Prototype Pattern Factory Method Abstract Factory
Primary Intent Step-by-step construction of complex multi-part objects Cloning pre-configured objects via clone() Subclasses decide which class to instantiate Creates families of related or dependent objects
Object Complexity High (many configurable parts & options) Heavy initialization cost, identical initial state Single product hierarchy Multiple product families / suites
Construction Mechanism Step-by-step calls via Director or Fluent Builder API Copy constructor / virtual clone() method Inheritance and polymorphic method override Object composition via abstract factory interface
Key Advantage Eliminates telescoping constructors Zero expensive re-initialization overhead Decouples creator from concrete product class Enforces compatibility among product families
When to Use Object has many optional parameters & representations Instantiating from scratch is costly or slow Object creation logic varies across subclasses System requires multi-platform component suites
